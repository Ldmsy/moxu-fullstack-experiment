# 我是谁

![“我是谁”项目封面](docs/assets/wo-shi-shui-cover-v02.png)

> AI 帮你整理，表达由你决定。

“我是谁”是一款帮助家庭主妇通过 AI 对话看见并认领日常创造、能力与兴趣，把被忽略的生活经验变成由自己确认的成长记录的应用。

## 我们看到的问题

许多家庭主妇承担大量长期、重复且难被量化的劳动，却很少有空间整理自己的感受、能力和创造。时间久了，个人价值容易只依赖家人反馈，“我做过什么、我擅长什么、我还想做什么”逐渐模糊。

## 我们的方案

产品以 AI 陪伴对话为入口，引导用户说出一件真实发生的小事。AI 负责整理和提出草稿，不替用户下定义；用户可以修改、删除或重新表达，再把自己确认的内容保存为成长卡片，并逐步形成能力画像和阶段回顾。每一次“认领”都由用户决定。

## 比赛现场完成

- 可运行的移动端网页和 Flutter App 工程；
- 手机号、页面验证码和密码注册登录；
- DeepSeek 流式对话、对话历史与固定安全分流；
- 成长卡片、能力画像、月度报告与隐私设置；
- 可主动开关、只用于当轮交流的临时表情辅助；
- 明确标注的伙伴探索示例页面。

当前 `main` 分支自动测试为 5 项，覆盖 Agent 规则、安全分流和前后端事件契约。

当前边界：页面验证码用于现场演示，不发送真实短信；伙伴探索为示例内容，不代表真人匹配已经上线；AI 对话需要在服务端配置有效的 DeepSeek API Key。

## 本地运行

```bash
npm install
cp .env.example .env
# 在 .env 中填写 DEEPSEEK_API_KEY
npm run dev
```

访问 `http://127.0.0.1:4173`。

## 使用方式

1. 打开网页，使用手机号、页面验证码和密码完成注册登录；
2. 进入对话页，用文字说出一件最近发生的小事，也可以自选开启表情辅助；
3. 结束对话后生成成长卡片，确认自己愿意认领的创造与能力；
4. 在“报告”和“我的”页面查看记录、能力线索与阶段回顾。

Flutter 工程位于 `shiguang_flutter/`。完成目标平台的 Flutter SDK 配置后，可在该目录执行 `flutter pub get` 和 `flutter run`。

## 实现说明

当前仓库已经接入移动端 UI，并保留最小前后端契约实验。Node 服务会直接提供 `新版网页/`，同时提供手机号账户接口和 DeepSeek 流式聊天接口。密码通过 `scrypt` 加盐保存，模型密钥只保存在服务端。

本地初版会把用户写入被 Git 忽略的 `.data/users.json`。验证码会直接显示在当前页面，不发送短信。部署到腾讯云前，只需要把数据适配器替换为 CloudBase 数据库，不需要开通腾讯云短信服务。

## 两个人怎么共同开发

- UI/UX：从 `main` 创建 `feat/ux-v1`，主要修改 `apps/web/`。
- 后端：从 `main` 创建 `feat/api-v1`，主要修改 `apps/api/`。
- 共同格式：修改 `packages/contracts/openapi.yaml` 必须同时更新测试并在 PR 中说明。
- PR 的自动检查通过后再合并，避免一方改坏另一方。

## 四人任务与建议评分权重

评分用于验收任务，不代表成员重要性。每个人都需要提交自己的分支和 Pull Request。

| 角色 | 协作分支 | 主要范围 | 权重 | 验收重点 |
|---|---|---|---:|---|
| UI/UX 与前端 | `feat/frontend-ux` | `apps/web/` | 30 | 页面可用、移动端适配、接口接入正确 |
| 后端与数据 | `feat/backend-api` | `apps/api/` | 30 | 接口可运行、错误处理、记录能力 |
| AI 与契约 | `feat/ai-contract` | `packages/contracts/`、后续 `packages/ai/` | 25 | 输出稳定、字段清楚、前后端都能理解 |
| 硬件与测试 | `experiment/hardware-test` | `tests/`、后续 `prototypes/` | 15 | 摄像头/灯光实验、测试记录、风险说明 |

总分 100。共同加分项：PR 描述清楚、没有越界修改、自动检查通过、能让另一位成员顺利接手。

## AI 协作规则

1. 先从自己的协作分支再创建短任务分支，例如 `feat/frontend-ux/home-v2`。
2. 给 AI 的任务要写明允许修改的目录，以及不能改变的接口字段。
3. AI 如果建议修改 `openapi.yaml`，必须先让前端和后端共同确认。
4. 不把未经检查的大批 AI 代码直接合入 `main`。
5. 最终通过 Pull Request 汇总到 `main`，不把四个人的代码一次性强推覆盖。
